### Q-002 BL-001 古いリンクへの対処方式

**Status**

解決済み

**Question**

テスト ディレクトリへ引き込むソースがリンクからコピーへ切り替わったとき、残っている古いシンボリック リンクを、どの方式で取り除きますか。

**Context**

- **経緯と背景**: `_collect_srcs.mk` は、inject ファイルまたはフィルター ファイルがあるソースを `CP_SRCS` (コピー) に分類し、ないソースを `LINK_SRCS` (リンク) に分類します。`makesrc_c_cpp.mk` の `generate_cp_src_rule` は、コピー先 (たとえば `console.c`) に古いリンクがあっても何もせず `cp -p <コピー元> <コピー先>` を実行します。コピー先のリンクがコピー元を指しているため、`cp` は同じファイルと判定して失敗します。
- **根拠資料**: [makesrc_c_cpp.mk の generate_cp_src_rule](../../../makefiles/makesrc_c_cpp.mk) (529 行から 557 行)、[makelibsrc_c_cpp.mk の generate_cp_src_rule](../../../makefiles/makelibsrc_c_cpp.mk) (633 行から 661 行)、[_collect_srcs.mk](../../../makefiles/_collect_srcs.mk)。同じ規則が 2 つのテンプレートに複製されています。方式を決めたあとは、両方に同じ修正を入れます (事実のため、この点は Q にしません)。
- **コードの読解で判明した追加の事実 (make での再現は未実施)**:
    - フィルター ファイルを通す経路は `cat <コピー元> | sh <フィルター> > <コピー先>` です。コピー先が古いリンクのままだと、シェルのリダイレクトはリンクを辿ってコピー元そのもの (`prod/` 配下の実体) を開いて空にします。`cp` の失敗と異なり、コピー元の内容が失われる経路です。コピー元は Git の追跡対象なので復元はできますが、BL-001 の記載にはない危険です。
    - 古いリンクのターゲットは、`make` から見るとコピー元と同じ更新時刻に見えます。このため、コピー先のルールが起動する条件は「inject ファイルまたはフィルター ファイルがコピー元より新しいこと」になります。inject ファイルを追加したあとにコピー元を編集すると、ルールが起動せず、リンクのまま inject なしでビルドが進む可能性があります。この点は、確認依頼として主エージェントに `make` での再現を依頼します。
- **各案の具体例**:

```make
# 案 A: コピーの前に、レシピの先頭で無条件に削除する
define generate_cp_src_rule
$(1): $(2) ...
	@rm -f $(1)
	@if [ -f "$(1).filter.sh" ]; then ...
```

```make
# 案 B (推奨): 概念を示す擬似コード。解析時に、既存のリンクの走査 (_makefw_source_link_scan) を使って
# CP_SRCS に含まれる名前の古いリンクを検出し、
# (1) そのターゲットを必ず再生成させ (強制の前提条件を足す)、
# (2) レシピの先頭でリンクを削除する
_STALE_CP_LINKS := $(filter $(addprefix ./,$(notdir $(CP_SRCS))),$(call _makefw_source_link_names,$(_makefw_source_link_scan)))
$(notdir $(_STALE_CP_LINKS)): _makefw_force_regen   # 空の規則で、常に新しい前提条件として働く
```

```make
# 案 C: 解析時 (make の読み込み時) に古いリンクを削除する
$(foreach l,$(_STALE_CP_LINKS),$(shell rm -f $(l)))
```

    - 案 A は変更が最小ですが、上記の「ルールが起動しない場合」を直しません。
    - 案 B は、古いリンクがあるときだけ再生成を強制し、削除はレシピ内で行います。`make -n` (ドライ ラン) がファイルを変えない性質を保ちます。解析時にリンクの走査を 1 回行う負荷が増えます (既存の `DIRECT_SRCS` の判定は `_DIRECT_EXISTS` が空でない場合だけ走査します)。
    - 案 C は単純ですが、`make -n` やターゲット指定なしの解析だけでもファイルを削除します。既存のテスト (`source_classification_selftest.py`) は「ドライ ランが構成ファイルを書かない」ことを確認しており、その方針と衝突します。

**Answer**

選択方式: 単一選択

- [ ] A: レシピの先頭で無条件に `rm -f` する。
- [x] B: (推奨) 解析時に古いリンクを検出して再生成を強制し、レシピの先頭で削除する。
- [ ] C: 解析時に古いリンクを削除する。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

### Q-009 逆向きの切り替わりで残る古いコピーの扱いの再確認

**Status**

解決済み

**Question**

inject ファイルやフィルター ファイルを削除して、引き込み方がコピーからリンクへ戻ったとき、Linux のテスト ディレクトリに残る古いコピーをどう扱いますか。実測の結果を踏まえて、あらためて選んでください。

**Context**

- **経緯と背景**: [Q-003](#q-003-bl-001-の逆向きの切り替わりコピーからリンクの扱い) では A (現状を仕様として維持し、文書に手順を明記) が選ばれました。ただし、Q-003 の **Context** は読解による推定で書かれており、実測の結果と、推奨の理由の前提に関わる事実を十分に伝えていませんでした。ユーザーの指示 (2026-11-25 の対話「Sonnet の掘り下げが浅いものは、書き直したり再質問をユーザーに行ってもよいです」) に基づき、事実を補って再確認します。Q-003 の回答は記録としてそのまま残します。
- **用語**: 「古いコピー」は、inject ファイルまたはフィルター ファイルがあった間に makefw がテスト ディレクトリへ作ったファイルです。「ローカル実体の優先」は、外部のソースと同名の通常のファイルがテスト ディレクトリにあれば、それを `DIRECT_SRCS` としてそのままコンパイルする、Linux の現在の動きです。
- **実測の結果** (2026-11-25。一時ディレクトリに makefw の `makefiles` と `bin_internal` を複製し、テスト ディレクトリ `app/probe/test/src/probeTest/aTest` へ `TEST_SRCS` で外部の `a.c` と `b.c` を引き込む構成で確認。リポジトリは変更していません):
    1. **フィルター ファイルを削除した場合**: フィルターを通した古いコピーが、そのまま使われます。その後にコピー元を編集しても、`make` は「'default' に対して行うべき事はありません」で終わり、編集は警告なしに無視されます。`ADD_SRCS` で引き込むソースの inject ファイルを削除した場合も同じです (全体管理文書の事前再現 (d))。
    2. **`TEST_SRCS` の inject ファイルを削除した場合**: 古いコピーの末尾に `#include "a.inject.c"` が残るため、コンパイルが `fatal error: a.inject.c: No such file or directory` で失敗します。失敗はしますが、原因が古いコピーであることは、このエラーからは読み取りにくい状態です。
    3. **`make clean` の動き**: `clean` は、`TEST_SRCS` と `ADD_SRCS` のうち外部のディレクトリにあるソースと同名のファイルを、分類によらず削除します ([makesrc_c_cpp.mk](../../../makefiles/makesrc_c_cpp.mk) の `MAKEFW_CLEAN_GITIGNORE_SRCS`、[_path_functions.mk](../../../makefiles/_path_functions.mk) の `_makefw_clean_external_sources`)。古いコピーは `clean` で消えます。利用者が意図してテスト ディレクトリに置いた同名の実ファイルも、同じく `clean` で消えます (同じ構成で確認)。
    4. **リポジトリでの使用例**: `app` 配下の `makepart.mk` と `makelocal.mk` の `TEST_SRCS` と `ADD_SRCS` を走査した結果、外部のソースと同名の実ファイルをテスト ディレクトリに置いて Git で管理している例はありません。`DIRECT_SRCS` になる管理対象の実ファイルは、どれも同じディレクトリを指す指定です (例: `app/cjson/test/src/libcjsonTest/mockCjsonTest/caller_info.c`)。これらは、下の案 B と案 C の対象外です。
    5. **Windows との違い**: Windows は、外部のディレクトリにあるソースと同名のローカル実体を `DIRECT_SRCS` から外し、コピーの対象へ戻して、コピー元の更新を追跡します ([_collect_srcs.mk](../../../makefiles/_collect_srcs.mk) の `EXTERNAL_SRCS`)。この処理のコメントは「コピー済みの実体を外部ソースの更新追跡から除外しない」です。同じ作業ツリーの状態でも、Linux は古いコピーを使い、Windows はコピー元を使います。
- **Q-003 の推奨の理由との関係**: Q-003 は「古いコピーと意図して置いた実ファイルを区別できず、自動削除は利用者のファイルを消す危険がある」ことを、案 A の主な理由にしていました。実測 3 のとおり、意図して置いた実ファイルは現在も `make clean` で消えるため、ローカル実体の優先は、`clean` をまたいで保たれる仕様ではありません。一方、`clean` をしていない作業ツリーで、意図して置いた実ファイルを自動で置き換えると、その内容は Git の管理外のため復元できません。
