### ログで確認した事実

- `mock_cplat` の各サブディレクトリは、1 回の `make` の中で 2 回たどられています。
    - 1 巡目 (ログ 5581 行目から): `make[5]` が `mock_cplat` に入り、`make[6]` として各サブディレクトリをゴールなしでビルドします。`crt` は 5614 行目で入り、6087 行目で出ています。

- 2 巡目では、ほとんどのサブディレクトリが `'_build_impl' に対して行うべき事はありません` を出しています。再コンパイルされたのは次の 3 ファイルだけです。
    - `crt/mock_cplat_fseek.cc` (1 巡目 5759 行目、2 巡目 6144 行目)
    - `crt/mock_cplat_ftell.cc` (1 巡目 5763 行目、2 巡目 6151 行目)
    - `trace/mock_cplat_tracer_set_name.cc` (1 巡目 6084 行目、2 巡目 6160 行目)
- この 3 ファイルは、`mock_cplat` のビルド全体で、コンパイル行に `-include .../mock_cplat/obj/auto_154a3c175fb5df44.h` (自動 PCH) が付いている 3 ファイルと一致します。ほかのコンパイル行には `-include` がありません。
- 失敗のメッセージ (6162 行目) は `make[6]`、つまり 2 巡目の親 (`mock_cplat`) が出しています。`crt/mock_cplat_ftell.cc` の 2 巡目のコンパイル行 (6151 行目) の直後です。

```text
make[6]: *** '../../lib/libmock_cplat.a' に必要なターゲット 'crt/obj/mock_cplat_ftell.o' を make するルールがありません.  中止.
```

### ソースで確認した事実

- 2 回たどる構造は、次の 2 つの依存から生じます。
    - `makemain.mk` の `default build clean run restore rebuild _gen _test_build: $(SUBDIRS)` により、`build` の前提としてサブディレクトリを 1 回たどります (1 巡目)。
    - サブディレクトリを持つライブラリでは `MAKEFW_IS_LEAF` が 1 になり、`build` のレシピが `_MAKEFW_LEAF_PARALLEL_RECIPE` で同じディレクトリの `make _build_impl` を起動します。その中で、アーカイブの規則 `$(OUTPUT_DIR)/$(TARGET): $(MAKEFW_ARTIFACT_DEPS) $(MAKEFW_ARTIFACT_OBJS)` の `MAKEFW_ARTIFACT_DEPS` が `$(SUBDIRS)` なので、サブディレクトリをもう 1 回たどります (2 巡目)。
- アーカイブの規則は、`$(SUBDIRS)` (サブディレクトリの再帰 make) と、`$(OBJS)` に含まれるサブディレクトリのオブジェクト (`SUBDIR_OBJS`。makefile の読み込み時に `filter_existing_source_objs.sh` が存在するファイルから列挙) を、同じ規則の前提に並べています。両者の間に順序の指定はありません。親の makefile には `crt/obj/*.o` を作る規則がありません。
- コンパイルの規則は `$(OBJDIR)/%.o: %.cc $(OBJDIR)/%.d ...` で、`.d` (依存ファイル) をオブジェクトの前提にしています。PCH を使ったコンパイルでは、コンパイルの成功後に `gcc_pch.py record` が `.d` へ PCH の依存を追記します (`depfile.write_text(text + addition)`)。PCH を使わないコンパイルでは、`record` は `.d` を書き換えません。

### 見立て (事前調査の時点。実行での裏付けは「原因の実行確認の結果」を参照)

失敗は、次の 2 つの要因が重なって起きたと考えています。

1. **要因 1 (2 巡目で再コンパイルが起きる)**: PCH を使ったオブジェクトは、`record` の追記によって `.d` の更新日時がオブジェクトより新しくなります。`.d` はオブジェクトの前提なので、次に規則が評価されると make はオブジェクトを古いと判定し、再コンパイルします。再コンパイルされた 3 ファイルが PCH を使った 3 ファイルと一致する事実と合います。この見立てが正しければ、失敗しなかったビルドでも、PCH を使うオブジェクトは 2 巡目で毎回再コンパイルされ、make を実行し直すたびにも再コンパイルされます。
2. **要因 2 (親が完了を待たずにオブジェクトを確認する)**: 2 巡目の親は、並列ビルドで `crt/` の再帰 make の完了を待たずに、前提の `crt/obj/mock_cplat_ftell.o` を確認します。再コンパイル中はオブジェクトが一時的に存在しない瞬間があり (アセンブラーが出力先を作り直すため、と考えていますが未確認です)、その瞬間に確認が当たると、親にはそのファイルを作る規則がないので `make するルールがありません` で止まります。

対策元 backlog の「`mock_cplat/crt` が並行して 2 回ビルドされた」という見立てとは異なり、2 回のビルドは並行ではなく順に実行されています。競合しているのは、2 巡目の `crt` の再コンパイルと、2 巡目の親の前提の確認です。

## 原因の実行確認の結果

[Q-002](#q-002-原因を裏付ける実行確認の担当と方法) の A に従い、WSL (Oracle Linux 8、GCC 8.5.0、GNU Make 4.2.1) 側の一時ディレクトリへ複製した最小構成で確認しました。  
リポジトリの作業ツリーではビルドしていません。

最小構成は、makefw `7087ed7` の複製と、`app/subfolder-sample` のライブラリ (`prod/libsrc/libsubfolder-sample`) を元にした共有ライブラリです。  
`subfolder_a` に、インクルード ガードのある共通ヘッダーを先頭で取り込むソースを 24 個置き、自動 PCH が使われる状態にしました。  
並列度は CI と同じ `MAKEFW_CPU_BUDGET=8` (make は `-j4`) です。

### 要因 1 の確認結果 (確定)

| 確認した内容 | 結果 |
| --- | --- |
| 何もない状態からの `make` (1 回) | PCH を使う 24 個が、1 巡目と 2 巡目で 1 回ずつ、計 2 回コンパイルされた。 |
| オブジェクトと `.d` の更新日時 | `.d` がオブジェクトより約 0.2 秒新しい (`gen_a_01.o` 07:10:02.691、`gen_a_01.d` 07:10:02.915)。 |

| `MAKEFW_GCC_PCH=0` (PCH を使わない) | 再実行で再コンパイルは 0 回。 |

Table: 要因 1 の確認結果

見立てのとおりです。  
自動 PCH を使うオブジェクトは、`gcc_pch.py record` の追記で `.d` がオブジェクトより新しくなり、`make` のたびに再コンパイルされます。  
サブディレクトリを持たないディレクトリでも、PCH を使うオブジェクトは同じ理由で毎回再コンパイルされます (1 巡目の `subfolder_a` 単独のビルドで確認)。

### 要因 2 の確認結果 (確定)

| 確認した内容 | 結果 |
| --- | --- |
| `gcc -c -o x.o` で既存のオブジェクトを上書きするときのシステム コール (`strace`) | アセンブラー (`as`) が `unlink("x.o")` の後に `openat("x.o", O_CREAT)` を行う。その間 (約 0.25 ミリ秒) はファイルが存在しない。 |

| 同じ条件で `MAKEFW_GCC_PCH=0` | 10 回中 0 回。再コンパイルが起きないため失敗しない。 |
| PCH なしで、サブディレクトリのソースを更新してから `make test` (存在しない時間は 0.3 秒) | 5 回中 5 回、同じメッセージで失敗した。 |

```text
make[1]: *** No rule to make target 'subfolder_a/obj/gen_a_01.o', needed by '../../lib/liblibsubfolder-sample.so'.  Stop.
```

親の make は、サブディレクトリの再帰 make の完了を待たずに、サブディレクトリのオブジェクトの存在を確認します。  
再コンパイルでオブジェクトが存在しない瞬間に確認が当たると、親にはそのファイルを作る規則がないので止まります。  
CI の失敗は、要因 1 が起こした再コンパイルに、この確認が当たったものと判断します。

最後の行は、要因 2 が PCH と無関係に単独でも起きることを示します。  
`make test` (`_test_build`) では、サブディレクトリの再帰 make とライブラリのリンク規則が同じ make の中で並列に処理されるためです。  
サブディレクトリのソースを更新して `make test` を実行する通常の作業でも、低い確率で同じ失敗が起きます。

### ほかの箇所への影響

- 実行体のテンプレート (`makesrc_c_cpp.mk`) は、ライブラリと同じ構造です。`.d` をオブジェクトの前提にする規則 (450 行目)、`record` の呼び出し (478 行目)、`$(MAKEFW_ARTIFACT_DEPS) $(MAKEFW_ARTIFACT_OBJS)` を並べるリンク規則 (379 行目) があり、要因 1 と要因 2 の両方が当てはまります (ソースの読解による確認)。
- Windows/MSVC には、どちらの要因も当てはまらないと判断します (ソースの読解による確認。実行はしていません)。`SUBDIR_OBJS` の列挙は Linux だけの処理で、Windows のリンク規則はオブジェクトのファイルを前提にしません。再コンパイルの要否は `_msvc_compile.mk` と `msvc_compile.ps1` がヘッダーと `.obj` の日時で判定し、`.d` の更新日時は使いません。
- 影響を受ける構成は、Linux で自動 PCH が有効になるすべてのディレクトリ (要因 1) と、サブディレクトリを持つすべてのライブラリと実行体 (要因 2) です。`makechild.mk` で `NO_LINK` を指定している箇所は、`cplat`、`mock_cplat`、`porter`、`mock_porter`、`cjson`、`struct_meta`、`subfolder-sample` などです。

### Q-004 要因 1 の修正の方法

**Status**

解決済み

**Question**

自動 PCH を使うオブジェクトが `make` のたびに再コンパイルされる問題を、どの方法で直しますか。

**Context**

原因は、コンパイルの後に `gcc_pch.py record` が `.d` へ追記し、`.d` がオブジェクトより新しくなることです ([原因の実行確認の結果](#要因-1-の確認結果-確定))。  
`.d` をオブジェクトの前提にする規則 (`$(OBJDIR)/%.o: %.c $(OBJDIR)/%.d`) は、`.d` が削除されたときに再コンパイルさせるための、GNU Make の一般的な書き方です。  
どの案も、この規則と `.d` の内容 (PCH と PCH 内のヘッダーへの依存) は変えません。

- 案 A: `gcc_pch.py record` が、追記の後に `.d` の更新日時をオブジェクトと同じにします。変更は `record` の数行です。一時複製での試作で、再コンパイルがなくなること、ヘッダーの更新と `.d` の削除では再コンパイルされることを確認済みです。

```python
depfile.write_text(text + addition, encoding="utf-8")
# 追記で .d がオブジェクトより新しくならないよう、更新日時をオブジェクトに合わせる。
target_stat = Path(arguments.target).stat()
os.utime(depfile, ns=(target_stat.st_atime_ns, target_stat.st_mtime_ns))
```

- 案 B: コンパイルの規則 (ライブラリと実行体の 2 つのテンプレート) で、`record` の後にオブジェクトを `touch` します。オブジェクトの更新日時が、コンパイルの完了より少し後になります。変更は 2 つのテンプレートに分かれます。

- 2 巡目: `build` のレシピ (`_MAKEFW_LEAF_PARALLEL_RECIPE`) が、並列度を決めて同じディレクトリの `make _build_impl` を起動し直します。その make の中で、リンクの規則の前提 `$(SUBDIRS)` が、各サブディレクトリを `_build_impl` ゴールでたどります。

リンクの規則の前提 `$(SUBDIRS)` は、`make test` (`_test_build`) の経路でも使われます。  
この経路は 1 つの make の中で 1 回しかたどらないため、変更の対象は `build` の経路だけです。

- 案 A: 1 巡目を残し、2 巡目をやめます。`build` のレシピが起動し直す make に「このディレクトリのサブディレクトリは処理済み」という印 (ディレクトリのパスを値とする変数) を渡し、その make ではリンクの規則の前提からサブディレクトリを外します。サブディレクトリから親のリンクだけを行う既存の経路 (`MAKEFW_ARTIFACT_ONLY`) と同じ考え方です。サブディレクトリへ渡るゴール、フックの順序、`NO_LINK` のサブディレクトリの下にあるネストしたサブディレクトリの扱いは、いまの 1 巡目のままです。

```makefile
# _flags.mk: build のレシピが起動し直す make へ、処理済みのディレクトリを渡す

MAKEFW_ARTIFACT_DEPS := $(if $(MAKEFW_ARTIFACT_ONLY)$(_MAKEFW_SUBDIRS_DONE),_makefw_artifact_recheck,$(SUBDIRS))
```

**Question**

**Context**

[Q-015](#q-015-testfw-の修正の-windows-での確認方法) の確認で見つかりました ([Windows での確認と試作の結果](#windows-での確認と試作の結果) の 3 行目と 4 行目)。  
Windows では、`make` を先に実行せずに `make test` を実行すると、サブディレクトリのテストがコンパイルされず、起点のテストだけが成功として報告されます。  
その後に `make` を実行しても、`make test` は「変更なし」と判定して省略し、不足した結果が残ります。  
`make` の後に `make test` を実行する通常の手順と CI では起きません。

原因は makefw のテンプレートにあり、修正の候補は 2 つのテンプレートの各 1 行です。

```makefile
# makesrc_c_cpp.mk / makelibsrc_c_cpp.mk (NO_LINK のディレクトリ)
# 現在
_test_build: $(OBJS)
# 修正の候補 (build の経路と同じ切り替え)
_test_build: $(if $(PLATFORM_WINDOWS),_msvc_compile,$(OBJS))
```

- 案 A: この案件で直します。対象のテンプレートは、この案件ですでに変更するファイルです。Windows 側の一時複製で、試作の効果を確認済みです。
- 案 B: この案件では直さず、残課題一覧に記録します。Windows で `make test` を単独で実行すると、サブディレクトリのテストが実行されない状態が残ります。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) この案件で直す。
- [ ] B: この案件では直さず、残課題一覧に記録する。
- [ ] C: その他

その他の回答 / 補足:

理由: テストが実行されていないのに成功として報告される動作で、気付きにくい不具合です。修正は小さく、対象のファイルはこの案件で変更します。Windows の一時複製で試作を確認済みです。
