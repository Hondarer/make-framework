## BL-001 makefw のスクリプトのテストが errors="replace" でデコード エラーを隠している

### 概要と問題点

- **現状の事象**: `framework/makefw/bin_test/` の Python テストの 8 ファイル、17 か所が、テキストの読み取りや子プロセスの出力の受け取りで `errors="replace"` を指定しています。リポジトリの規範 `app/general/docs/python-text-encoding-guideline.md` は、デコード エラーを隠す目的で `errors="ignore"` や `errors="replace"` を指定することを禁じています。2026-11-25 時点の該当箇所は次のとおりです。
    - `app_paths_selftest.py` 29 行目
    - `app_compile_budget_selftest.py` 286 行目
    - `gcc_pch_selftest.py` 509、511 行目
    - `test_app_compile_budget.py` 112、282、367 行目
    - `test_build_signature.py` 67 行目
    - `test_nested_parallel.py` 77 行目
    - `test_path_spaces.py` 59、123、145、156、174、223、264 行目
    - `test_stage_elapsed.py` 70 行目
- **本来あるべき姿**: テキストは `encoding="utf-8"` を明示して厳密にデコードし、UTF-8 以外を出しうる子プロセス (Windows の `cl.exe` など) の出力は、バイト列で受け取って、出力の仕様に合わせて個別にデコードする状態です。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り。継続作業 `261125-makefw-backlog` で BL-029 (`encoding` の指定漏れ) を調べた際に、構文木の走査で見つけました。
- **今回の見送り理由**: BL-029 の範囲 (`encoding` の指定漏れ) の外です。子プロセスの出力のデコード方式の変更を伴い、Windows での検証が要るため、ユーザーの回答 (検討用 Markdown `261125-makefw-backlog-discussion.md` の Q-005、選択肢 A) により、別の残課題として残しました。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: 上記の `framework/makefw/bin_test/` の 8 ファイル。
- **放置した場合のリスク**: 文字コードの誤りが置換文字に化けて隠れ、テストの失敗の原因の調査で、出力の内容を正しく読めない場合があります。優先度を低としたのは、テストの合否の判定そのものは主に終了コードとファイルの有無で行っており、製品のビルドには影響しないためです。

### 推奨される対応策

- **恒久対応案**: 子プロセスの出力は `capture_output=True` のバイト列で受け取り、Linux では UTF-8、Windows の MSVC の出力はその仕様に合わせた文字コードで、`errors` を指定せずにデコードします。ファイルの読み取りは `encoding="utf-8"` だけを指定します。Windows 側で `bin_test` を実行して確認します。
- **参考情報**: `app/general/docs/python-text-encoding-guideline.md` の「子プロセスとのテキスト通信」、検討用 Markdown `261125-makefw-backlog-discussion.md` の Q-005。

## BL-002 Windows で inject ファイルやフィルター ファイルを削除しても、古いコピーが使われ続ける可能性がある

### 概要と問題点

- **現状の事象 (読解による推定、未検証)**: Windows は、テスト ディレクトリへ引き込むソースをすべてコピーで引き込みます。コピーの規則 (`makesrc_c_cpp.mk` と `makelibsrc_c_cpp.mk` の `generate_cp_src_rule`) の前提条件は、コピー元と、存在する inject ファイルとフィルター ファイルだけです。inject ファイルやフィルター ファイルを削除しても、コピー先 (inject の結合やフィルターの適用で、コピー元より新しい更新時刻を持つ) が最新と判定され、コピーの規則は再実行されないと考えられます。その結果、コピー元を次に編集するか `make clean` を実行するまで、次の状態が続く可能性があります。
    - `TEST_SRCS` の inject ファイルを削除した場合: 古いコピーに残る `#include "<名前>.inject.c"` のため、コンパイルが失敗する。
    - フィルター ファイルを削除した場合: フィルターを通した古い内容のままコンパイルされる。
- **本来あるべき姿**: inject ファイルやフィルター ファイルを追加・削除した次のビルドで、コピーがその時点の構成で作り直される状態です。

### 経緯と見送り理由

- **摘出契機**: 継続作業 `261125-makefw-backlog` で、Linux の逆向きの切り替わり (検討用 Markdown の Q-009) の扱いを決めた後、Windows の規則を読解して気付きました。
- **今回の見送り理由**: この案件で合意した範囲は、Linux の切り替わり (BL-001) です。Windows では未検証で、作り直しの判定には、コピー時の構成 (inject とフィルターの有無) の記録が要るため、別途の設計が必要です。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: Windows の既存の作業ツリーで、テスト ディレクトリの inject ファイルやフィルター ファイルを削除する変更を取り込んだ利用者。新しく取得した作業ツリーと CI では起きません。
- **放置した場合のリスク**: 原因の分かりにくいコンパイルの失敗や、古い内容のままのテストの実行が起き、`make clean` を要します。

### 推奨される対応策

- **恒久対応案**: まず Windows で、inject ファイルを追加してビルドした後に削除し、次のビルドの結果を確認します。再現した場合は、コピー時の構成 (inject とフィルターの有無) を `OBJDIR` に記録し、解析時に現在の構成と比べて異なればコピーの規則を必ず実行させます (記録の読み取りだけを解析時に行い、`make -n` ではファイルを変えない)。
- **参考情報**: `framework/makefw/makefiles/_collect_srcs.mk`、`makesrc_c_cpp.mk` と `makelibsrc_c_cpp.mk` の `generate_cp_src_rule`、継続作業 `261125-makefw-backlog` の最終仕様 (Linux の切り替わりの処理)。

## BL-003 mock のヘッダーを変えた後の MSVC の差分ビルドで、古いオブジェクトが残った事象が再現しない (再発時の調査)

### 概要と問題点

- **現状の事象**: 2026-11-25 に、`app/cplat/test/include/mock_cplat.h` から関数 (`cplat_socket_shutdown_receive`) を消した後の Windows の差分ビルドで、`app/cplat/test/libsrc/mock_cplat/obj/md/mock_cplat_expand_format.obj` などが作り直されず、古い `/include:_mock_impl_cplat_socket_shutdown_receive` が残ってリンクが `LNK2001` で失敗したと報告されました。`make -C app/cplat clean` の後のビルドでは解消しました。継続作業 `261125-makefw-backlog` で Windows 側で再現を試みましたが、再現しませんでした。
    - ヘッダーの更新時刻だけを進めると、`find_dirty_srcs.sh` が `mock_cplat.cc` と `mock_cplat_expand_format.cc` を作り直しの対象として出力し、両方が再コンパイルされました。
    - ヘッダーに `MOCK_CPLAT_LINK_IMPL(makefw_bl002_probe)` を加えると、期待どおり `LNK2001` になりました。元に戻した後の差分ビルドとテストは成功し、古い記号を持つ `.obj` と `.pch` は 0 件でした。
- **本来あるべき姿**: ヘッダーを変えた後の差分ビルドで、そのヘッダーを取り込むオブジェクトが必ず作り直される状態です。

### 経緯と見送り理由

- **摘出契機**: 過去 backlog からの転記 (`app/general/docs/prompts/current/261123-remaining-backlog-items-backlog.md` の BL-002)。
- **今回の見送り理由**: 再現しないため、原因を特定できず、修正と再現テストを作れません。最終仕様では、再現しない場合の扱いをユーザーに確認するとしていましたが、ユーザーの指示 (2026-11-25 21:48 頃の対話「決定した最終仕様が実現できない場合は、ユーザーに問い合わせることなく backlog に送る」) により、再発時の調査に残す残課題として送りました。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: Windows の手元の差分ビルド。`framework/makefw` の MSVC の依存の記録 (`bin_internal/msvc_compile.ps1`、`_msvc_pch.ps1`、`find_dirty_srcs.sh`、`makefiles/_msvc_compile.mk`)。CI は毎回作り直すため影響しません。
- **放置した場合のリスク**: 再発すると、原因の分かりにくいリンクの失敗が起き、`clean` を要します。優先度を低としたのは、再現手順で再現せず、`clean` で回避できるためです。

### 推奨される対応策

- **恒久対応案**: 再発した時点で、`clean` の前に次を保存し、継続作業 `261125-makefw-backlog` の全体管理文書の「Windows 側への依頼手順 (BL-002)」の仮説 H1 から H5 に当てはめます。
    - 該当の `obj/md/*.d`、`*.cc.json`、`auto_*.pch.deps.json`
    - ヘッダー、`.obj`、`.d`、`.pch` の更新時刻 (`ls -l --time-style=full-iso`)
    - `find_dirty_srcs.sh` の単独の実行結果と `make -n` の出力
    - 直前に行った Git の操作 (ブランチの切り替えや、サブモジュールの更新による更新時刻の巻き戻りの有無)
- **参考情報**: 継続作業 `261125-makefw-backlog` の最終仕様 `261125-makefw-backlog-design.md` の「BL-002」の章 (仮説と見分け方、再現の結果)。
