## BL-001 subfolder-compilation.md が存在しない app と古い実装を例にしている

### 概要と問題点

- **現状の事象**: `framework/makefw/docs/subfolder-compilation.md` は、ディレクトリ構成と生成物の例に `app/hierarchy-example` を使っていますが、この app は存在しません (実在するのは `app/subfolder-sample`)。「再帰的 make 処理」で引用している `makemain.mk` の内容も、現在の実装 (`SUBDIRS` の明示指定時の直列化、OS による除外、`test` の 2 フェーズなど) と異なります。
- **本来あるべき姿**: 例が実在する app と一致し、引用が現在の実装と一致すること。

### 経緯と見送り理由

- **摘出契機**: 原因の調査で、最小構成の複製元を文書の例から探したとき。
- **今回の見送り理由**: この案件の目的 (並列ビルドの失敗の修正) と関係しない、文書全体の見直しになるためです。この案件では、修正に関係する節への追記だけを行います。
- **継続作業での経緯と対処**: 2026-11-16、ユーザーの依頼により、見送りをやめてこの案件で対応することになりました。文書と実装を照合した結果、次の 2 点が分かりました。1 点目は、例の `app/hierarchy-example` が、規範 (`app/general/docs/agents-and-skills-guideline.md` の「framework の文書では `app/example` などの架空名を使い、実在 app のパスを正本にしません」) に沿った架空の名前だったことです。「存在しない app を例にしている」こと自体は問題ではなく、下記の恒久対応案 (実在する app への置き換え) は規範と合いません。問題は、架空の例の中に実在する app の名前が混ざっていることでした。2 点目は、`makemain.mk` の引用のほかにも、実装との相違 (TEST_SRCS の収集の説明、makefile のテンプレートの引用、例の中の不整合) があることです。その後、次の方針で合意しました。例は架空の名前を維持し、混ざっている実在の名前を架空の名前にそろえます (Q-010 の A)。見つかった相違をすべて直し、テスト レポートの出力例も実際の出力と照合して直します (Q-011 の C)。実装の引用は数行の抜粋に絞ります (Q-012 の A)。照合に使う実際の出力の入手方法を、Q-013 で確認しています。

### 影響範囲とリスク

- **影響対象**: `framework/makefw/docs/subfolder-compilation.md` の読者。
- **放置した場合のリスク**: 文書の例のとおりに確認しようとしても対象が見つからず、調査や学習に余分な時間がかかります。

### 推奨される対応策

- **恒久対応案**: 例を `app/subfolder-sample` の実際の構成に置き換え、`makemain.mk` の引用を現在の実装に合わせます。引用は、変更に追従しやすいよう要点だけに絞ります。
- **参考情報**: `app/subfolder-sample`、`framework/makefw/makefiles/makemain.mk`。

## BL-002 text_style_jp.py の --in-place が改行を CRLF に変え、大きなファイルで時間がかかる

### 概要と問題点

- **現状の事象**: Windows で `python framework/docsfw/bin/text_style_jp.py --in-place <file>` を実行したところ、改行が LF だった Markdown (約 1,300 行) の改行がすべて CRLF に変わりました。リポジトリの方針は LF です (`.gitattributes` の `* text=auto eol=lf`)。また、同じファイルの `--dry-run` に 72 秒かかりました (約 50 行のファイルでは 5 秒)。
- **本来あるべき姿**: `--in-place` が元の改行を保つこと。行数に対して処理時間が極端に伸びないこと。

### 経緯と見送り理由

- **摘出契機**: この案件の検討用 Markdown を整形したとき (2026-11-16)。改行は手作業で LF に戻しました。
- **今回の見送り理由**: 対象が `framework/docsfw` で、この案件の対象 (makefw と testfw) と関係しないためです。原因は調べていません。
- **継続作業での経緯と対処**: 2026-11-16、改行コード保持と処理時間の双方を対処し、本件はクローズしました。1) 改行コード保持: `framework/docsfw/bin/text_style_jp.py` で読み込み時に `newline=""` で元の改行コード (LF / CRLF / CR) を判定し、`--in-place` と `--output` の書き込み時に `newline=line_ending` を指定して元の改行コードを保持するよう修正しました (docsfw コミット `f58d78b`、ワークスペース参照更新 `f25759f7`、回帰テスト追加済み)。2) 処理時間の短縮: `framework/docsfw/bin_internal/text_style_jp_engine.py` のプロファイル計測で、`_replace_skip_existing` の未出現語に対する文字単位走査、`_apply_add_space_pairs` でのセグメントごとの毎回ソートと全件正規表現コンパイル、`_protect_no_space_words` での毎回分類がボトルネックと判明したため、早期リターン・キャッシュ・遅延コンパイルを実装しました (docsfw コミット `2a0f1df`、ワークスペース参照更新 `8dbc1f52`)。975 行の Markdown に対する `--dry-run` は 72.51 秒から 5.77 秒へ、52 行の Markdown は約 5 秒から 2.77 秒へ短縮され、既存テスト (`--test`) および `--dry-run` 出力の一致を確認しました。

### 影響範囲とリスク

- **影響対象**: Windows で `text_style_jp.py` を実行する作業 (改行コード保持・処理時間ともに対処済み)。
- **放置した場合のリスク**: なし (対処済みのためクローズ)。

### 推奨される対応策

- **恒久対応案**: 改行コードの保持および処理時間の最適化の双方とも対処済みです。
- **参考情報**: `framework/docsfw/bin/text_style_jp.py`、`framework/docsfw/bin_internal/text_style_jp_engine.py`、`framework/docsfw/docs/text_style_jp.md`。
